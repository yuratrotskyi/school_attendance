# Дизайн: окрема команда 10+ періодів з вкладки "Відвідуваність"

## 1. Мета
Додати окрему CLI-команду, яка заходить у `Журнали -> Відвідуваність`, проходить по класах у dropdown і формує окремий звіт лише по учнях, які були відсутні **10 навчальних днів або більше підряд**.

Ця команда не повинна запускати повний пайплайн `run-daily` і не повинна створювати інші артефакти щоденної звітності.

## 2. Узгоджені правила
- Джерело даних: вкладка `Відвідуваність`, а не предметні журнали.
- У звіт потрапляють лише учні з періодами `>= 10` навчальних днів підряд.
- Якщо в одного учня за семестр кілька таких періодів, **кожен період виноситься окремим рядком**.
- Формати виводу: `csv` і `xlsx`.
- Назви файлів і стовпців: українською.

## 3. Межі фічі
### 3.1 Що команда робить
- авторизується в `nz.ua`;
- відкриває сторінку `Журнали`;
- переходить у вкладку `Відвідуваність`;
- перебирає класи зі списку;
- читає attendance-дані по днях для кожного класу;
- знаходить 10+ періоди;
- пише лише два вихідних файли.

### 3.2 Що команда не робить
- не створює `report.md`;
- не створює `detail.csv/.xlsx`;
- не створює `student-absence-summary.csv/.xlsx`;
- не створює `відсутність-сьогодні-вчора.csv/.xlsx`;
- не збирає дані з предметних журналів.

## 4. Назва команди
Рекомендована назва:

- `run-attendance-10plus`

Логіка назви:
- `run-...` узгоджується зі стилем `run-daily`;
- `attendance` явно відділяє новий сценарій від предметних журналів;
- `10plus` показує, що команда вузькоспеціалізована.

## 5. Формат файлів
Вихідні файли пропонуються такими:

- `періоди-відсутності-10-днів-відвідуваність.csv`
- `періоди-відсутності-10-днів-відвідуваність.xlsx`

Стовпці:
- `ID учня`
- `Учень`
- `Клас`
- `Період від`
- `Період до`
- `К-сть навчальних днів`

Файли створюються в `out/<run_date>/`.

Якщо періодів немає:
- файли все одно створюються;
- вони містять лише заголовки.

## 6. Архітектура
### 6.1 CLI
У `cli.py` додається новий subcommand `run-attendance-10plus`.

Параметри пропонуються такими:
- `--run-date`
- `--dry-run`
- `--skip-collect`
- `--raw-file`
- `--class` (repeatable)
- `--env-file`

### 6.2 Pipeline
У `pipeline.py` додається окремий lightweight pipeline, який:
- збирає attendance-overview raw data або читає локальний raw CSV;
- нормалізує дані в `AttendanceRecord`;
- reuse-ить наявну функцію `build_ten_day_absence_periods(...)`;
- пише лише один attendance-only report bundle.

### 6.3 Collector
У `collector.py` додається окремий collector для вкладки `Відвідуваність`.

Важливий принцип:
- новий collector не втручається в існуючий збір з `/journal/list`;
- старий `collect_raw_exports(...)` лишається без зміни поведінки;
- новий вхідний шлях буде окремим, наприклад `collect_attendance_overview_exports(...)`.

### 6.4 Reporting
У `reporting.py` додається окремий writer для attendance-only 10+ звіту:
- CSV з українськими заголовками;
- XLSX з тим самим набором рядків.

## 7. Представлення даних
Щоб reuse-нути наявну аналітику, attendance-overview collector повертає записи, сумісні з `AttendanceRecord`:

- `lesson_no = 1` як синтетичне значення на рівні дня;
- `status = ABSENT` або `PRESENT`;
- `reason_code` можна лишати порожнім.

Цього достатньо, бо `build_ten_day_absence_periods(...)` працює на рівні навчальних днів і визначає день відсутності через `any(status == "ABSENT")`.

## 8. Selector config
У `config/nz_selectors.json` додається нова секція, наприклад `attendance_overview`, де будуть:
- URL сторінки;
- селектор вкладки `Відвідуваність`;
- селектор dropdown класів;
- селектори рядків/клітинок таблиці;
- опційні параметри wait/retry.

Це дозволить підлаштовуватися під зміни DOM без переписування collector’а.

## 9. Ризики і захист
Основний ризик: DOM вкладки `Відвідуваність` може відрізнятися від предметних журналів і бути частково віртуалізованим.

Тому collector повинен працювати в 2 шари:
- спершу спроба витягнути дані з `window.__INITIAL_STATE__` / `__NUXT__` / подібного payload;
- якщо даних там немає, fallback на DOM extraction.

Це той самий патерн, який уже використовується в предметних журналах, тож ризик регресії мінімальний.

## 10. Тестування
Потрібно покрити:
- CLI dispatch нової команди;
- analytics/reporting на окремий attendance-only bundle;
- collector helpers:
  - витяг класів із dropdown;
  - перетворення attendance-overview даних у `AttendanceRecord`;
  - фільтр `--class`;
- dry-run pipeline:
  - створюються лише attendance-only `csv/xlsx`;
  - рядки містять кожен 10+ період окремо;
  - при відсутності періодів файли містять тільки заголовки.
